# RPG EIRDAN — ОСНОВНАЯ ИНСТРУКЦИЯ РАЗРАБОТКИ

Eirdan — долгосрочный модульный RPG-проект. Основной клиент разработки — Godot/Android. Существующий PWA сохраняется как рабочая референсная реализация и источник уже проверенных механик до их осознанного переноса.

Приоритет: работающий результат, правильная архитектура, расширяемость, data-driven настройка, тестируемость, диагностика и безопасное обновление. Работающая функция в неправильном месте архитектуры не считается завершённой.

## 1. Репозиторий — источник истины

Перед существенным изменением сначала изучить актуальный код и документацию репозитория. Не угадывать файлы, функции, сцены, интерфейсы, зависимости, форматы данных, package contracts и состояние реализации.

Проверить:
- какая система должна владеть функцией;
- нет ли уже полной/частичной реализации;
- нет ли дубля, legacy или compatibility-кода;
- можно ли расширить существующий правильный интерфейс;
- какие системы, данные, saves, packages, Android runtime, diagnostics и тесты затрагиваются;
- является ли старая PWA-реализация полезной спецификацией поведения для переноса.

Если требование существенно неоднозначно — уточнить. Иначе реализовывать без лишнего согласования.

## 2. Архитектура и владельцы ответственности

Разделять проект по ответственности: app/runtime, core, modules, packages/update, data/overrides, world, map, travel, character, inventory, combat, AI, simulation, persistence/save, diagnostics, Android integration, audio, UI, tools/editors и новые самостоятельные области по необходимости.

Каждая система имеет:
- одну понятную ответственность;
- владельца состояния;
- публичный интерфейс;
- явные зависимости;
- диагностический контракт;
- тесты/validation gate по необходимости.

UI/Control/Scene отображает состояние и передаёт действия системам. UI не является источником игрового состояния и не владеет игровыми правилами.

Godot Scene Tree не должен превращаться в глобальное хранилище бизнес-логики. Gameplay/domain state принадлежит системам и моделям данных, а Nodes являются адаптерами там, где это возможно.

## 3. Composition root и модули

Независимые системы соединяются через явный composition root/runtime bootstrap, а не случайными ссылками между внутренностями модулей.

Опциональные модули должны включаться/отключаться независимо.

Отключённый модуль по возможности:
- не инициализируется;
- не выполняет побочные эффекты;
- не участвует в тестах активного домена;
- не запускает нерелевантный CI;
- не может сломать активную игру своей внутренней ошибкой.

Зависимости модулей объявляются явно. Нельзя включить модуль без обязательных зависимостей.

Autoload использовать только для действительно runtime-wide сервисов с чёткой ответственностью. Не превращать Autoload в свалку глобального состояния.

Общее core содержит только действительно общие примитивы.

## 4. Android Runtime и APK

APK — стабильная оболочка/runtime, а не контейнер, в который обязательно зашивается каждое изменяемое значение игры.

APK обновляется, когда меняются:
- Godot/runtime;
- Android permissions/manifest;
- Android plugins, Java/Kotlin;
- native libraries/GDExtension;
- bootstrap/package loader;
- фундаментальные runtime contracts;
- другие изменения, которые объективно требуют новой бинарной сборки.

Обычное изменение данных или контента не должно требовать новой APK-сборки, если его можно корректно выразить через data/package layer.

Не стремиться к «APK никогда не обновляется». Цель: APK обновляется осмысленными блоками, а не после каждой правки данных.

Основной Android target — arm64. Расширять ABI только при реальной необходимости.

## 5. Packages и обновления

PackageManager владеет проверкой, staging, activation, active/previous state и rollback. Источники пакетов не владеют активацией.

GitHub, HTTP-сервер, локальный Android file picker и будущие источники — сменные transports/sources.

Безопасная установка:
источник → manifest validation → compatibility validation → staging → SHA-256/integrity → content validation → activation → сохранение предыдущей рабочей версии → cleanup позже.

Рабочий пакет не удалять до успешной проверки нового.

Повреждённый/несовместимый пакет не должен ломать активную игру.

Игра должна запускаться offline с последней активной рабочей версией пакетов.

Package format, runtime compatibility, dependencies и schema имеют версии.

Удалённый updater не должен быть привязан к GitHub настолько, чтобы смена хостинга требовала переписывать PackageManager.

## 6. Data-driven проект

Изменяемые игровые значения по умолчанию хранить как данные, если они не являются алгоритмом.

К данным относятся, где это разумно:
- имена и названия;
- характеристики предметов;
- скорость перемещения;
- цены;
- параметры классов/способностей;
- NPC/content definitions;
- карты, POI, дороги, terrain;
- таблицы баланса;
- локализация;
- ссылки на ресурсы;
- другие authorable значения.

Если изменение имени NPC, урона меча или скорости путешествия требует пересборки APK, сначала проверить архитектуру: вероятно, значение лежит не в том слое.

Gameplay systems получают итоговые значения через DataRegistry/публичный data API, а не читают произвольные override-файлы напрямую.

Базовые данные неизменяемы пользователем. Пользовательские правки создают override layer.

Порядок разрешения:
base → official packages → user packages/mods → session/runtime overrides, если они предусмотрены конкретной системой.

Для итогового значения должна быть доступна provenance: откуда оно пришло и какой слой его переопределил.

## 7. Редакторы и пользовательская настройка

Цель — максимально позволять редактировать поддерживаемые данные без изменения исходного кода.

Редактор является authoring-инструментом, а не владельцем игровых правил.

Редактор:
- читает публичную схему данных;
- валидирует ввод;
- создаёт/изменяет override/content package;
- показывает ошибки;
- по возможности показывает источник текущего значения;
- не записывает правила в UI-код.

Map Editor остаётся примером подхода для будущих редакторов предметов, баланса, NPC и других данных.

Не создавать универсальный «редактор всего», если разные домены требуют разных правил валидации. Общими могут быть package/data primitives, но доменные editors сохраняют собственную ответственность.

## 8. Структура Godot-файлов

Каждый нетривиальный исходный файл должен иметь короткую пометку ответственности.

Крупные файлы делить заметными комментариями на смысловые блоки только внутри одной ответственности.

Если разметка показывает несколько независимых систем внутри одного файла — разделить файл.

Предпочитать небольшие публичные API и явные зависимости.

Не полагаться на editor-generated cache или неявные global class dependencies там, где чистый headless/CI запуск должен работать. Критичные инфраструктурные зависимости подключать явно.

Scenes/resources организовывать по доменам. Не складывать независимые системы в одну сцену ради удобства.

## 9. Research-first

Для нетривиальных задач при необходимости использовать интернет.

Приоритет:
1. официальная документация Godot/Android и спецификации;
2. зрелые библиотеки и open-source;
3. известные алгоритмы и архитектурные паттерны;
4. похожие игровые системы;
5. практический опыт разработчиков/форумы/Reddit как дополнительный источник.

После исследования выбирать:
1. встроенное/готовое проверенное решение;
2. адаптацию зрелого подхода;
3. собственную реализацию.

Зависимость или Android plugin добавлять только при реальной пользе с учётом размера, поддержки, лицензии, совместимости, Android lifecycle и связанности.

Не копировать чужой код вслепую.

## 10. Чистота проекта и legacy PWA

Старый PWA пока не удалять и не переписывать без необходимости. Он является:
- рабочей исторической реализацией;
- источником уже проверенного поведения;
- материалом для сравнения при переносе систем.

Новый Godot-код не должен зависеть от DOM/PWA runtime.

Не переносить старую архитектуру файл-в-файл. Переносить contracts, правила, данные и проверенное поведение в правильные Godot/Android boundaries.

Связанный с изменяемой системой архитектурный долг исправлять сразу. Несвязанный глобальный рефакторинг не проводить.

После завершённого переноса конкретного домена старый код удалять только отдельным осознанным решением после проверки зависимостей и parity.

## 11. Данные и saves

Постоянные данные имеют владельца, формат и версию.

Разделять:
- immutable/base content;
- installed package content;
- user overrides/mods;
- mutable save/session state;
- transient runtime state.

При изменении persistent state учитывать schema version, старые saves, миграции, валидацию и диагностику повреждений.

Save не должен копировать в себя весь баланс/контент без необходимости. Хранить идентичность и изменяемое состояние, а определения получать через data layer, если это совместимо с требованиями сохранений.

Изменение активных пакетов должно быть диагностируемым, чтобы можно было понять, с каким набором данных был создан/загружен save.

UI/Scene Tree не является каноническим persistent state.

## 12. Ассеты

Код, данные и тяжёлые ассеты имеют разные жизненные циклы.

Карты, музыка, изображения, шрифты и другие тяжёлые ресурсы должны по возможности обновляться независимо и не заставлять повторно скачивать неизменившийся контент.

Для пакетов/ассетов использовать version/content hash.

Безопасная замена:
загрузка/импорт → проверка → декодирование/валидация при необходимости → активация → удаление старой версии позже.

Рабочую копию не удалять до проверки новой.

Не помещать изменяемые runtime-файлы в слой, предназначенный только для packaged `res://`, если им требуется запись/замена. Mutable runtime content хранить в `user://` или другом корректном Android storage abstraction.

## 13. Диагностика — часть каждой системы

Новая значимая система не считается завершённой без диагностического контракта.

Диагностика наблюдает систему через публичное состояние/events и не дублирует игровые правила.

Каждый домен по необходимости предоставляет:
- snapshot;
- validation/invariants;
- meaningful events;
- errors/warnings;
- version/package/schema information;
- performance counters, если они полезны.

Использовать уровни ERROR/WARN/INFO/DEBUG/TRACE.

Не логировать бесконтрольно каждое действие сотен NPC. Подробный TRACE включать адресно.

Для связанных действий использовать correlation/action ID, когда это помогает проследить цепочку между системами.

Crash/diagnostic snapshot должен по возможности содержать:
- runtime/Godot/Android version;
- build/package versions and hashes;
- save/schema version;
- активные packages/mods;
- последние значимые events/actions;
- состояние затронутых систем;
- ошибки/stack;
- безопасную информацию об устройстве/runtime.

Диагностический export должен быть доступен пользователю через Android-системный механизм сохранения/шаринга.

## 14. Тесты и CI

Проверки соответствуют архитектурным доменам.

Минимальная цепочка после изменения GDScript/runtime:
изменение → static contracts при наличии → Godot parse/headless boot → domain regression/integration → Android export gate при затронутом Android/runtime → только затем считать блок рабочим.

Godot exit code 0 не является достаточным доказательством. CI должен также отслеживать SCRIPT ERROR, Parse Error, Failed to load script и другие известные блокирующие классы ошибок.

Новый класс ошибки, прошедший старые gates, по возможности закреплять новой проверкой.

Отключённый Combat не должен блокировать изменение PackageManager/World/Map без причины.

Каждый значимый домен имеет собственный validation/test gate.

Полный integration gate нужен:
- перед значимым релизом;
- при изменении общего core/runtime/contracts;
- при изменении package/data/save compatibility;
- перед включением отключённого модуля.

После изменений проверить:
- архитектуру и дубли;
- зависимости/preloads/autoloads;
- GDScript parse и headless module-load;
- regression/diagnostic/integration затронутого домена;
- saves/migrations;
- package compatibility/integrity/rollback;
- Android export, если затронут runtime/platform;
- фактический результат CI.

Не объявлять PASS до фактического результата.

## 15. Android-проверка

Headless CI не заменяет тест на реальном Android для платформенных функций.

На реальном устройстве проверять по необходимости:
- установка/обновление APK;
- startup;
- lifecycle/background/resume;
- Android file picker/SAF;
- package import/update/rollback;
- offline startup;
- diagnostics export/share;
- permissions;
- touch/input;
- performance/memory;
- восстановление после повреждённого пакета.

Ручное тестирование пользователем должно выдавать диагностический файл, достаточный для анализа без необходимости вручную переписывать логи.

## 16. Документация

Документация должна соответствовать коду.

Поддерживать по необходимости:
- ARCHITECTURE;
- SYSTEMS;
- PROJECT_LAYOUT;
- DATA_FORMATS;
- DECISIONS;
- ROADMAP;
- PROGRESS;
- DIAGNOSTICS;
- IMPLEMENTED;
- package/update format documentation.

`IMPLEMENTED.md` описывает кратко существующие пользовательские/системные возможности. Это не changelog и не список мелких технических шагов.

Пример правильного уровня:
- «Поддерживается безопасная установка и rollback пакетов».

Неправильный уровень:
- «Создали manifest.json, добавили поле id, затем SHA-256».

## 17. Релизы и версии

Разделять версии:
- APK/runtime;
- game/core;
- package/content;
- save schema;
- diagnostics format;
- assets при необходимости.

APK version не должна автоматически означать версию всех данных игры.

Диагностика должна позволять восстановить точную комбинацию runtime + packages + schema, на которой возникла ошибка.

Release metadata обновлять согласованно с реально выпускаемым слоем.

PWA Service Worker/build metadata относятся только к legacy PWA и не являются обязательной частью Android/Godot релиза.

## 18. Обучение через разработку

После существенных изменений кратко показывать:
- что и зачем изменено;
- файл/систему;
- небольшой реальный фрагмент;
- использованные Godot/GDScript/Android конструкции или API;
- как это связано с архитектурой;
- как проверено.

Новые конструкции объяснять простым языком на фактическом коде Eirdan.

Не разбирать каждую строку и не упрощать архитектуру ради обучения.

## 19. Перед существенным изменением

Перед реализацией определить:

1. Кто владеет ответственностью?
2. Есть ли существующая Godot-реализация?
3. Есть ли полезная PWA-реализация/contract для переноса?
4. Не получает ли система чужую ответственность?
5. Через какой публичный интерфейс системы взаимодействуют?
6. Это алгоритм, persistent state или изменяемые данные?
7. Можно ли вынести значение в data/override/editor вместо APK-кода?
8. Можно ли отключить модуль независимо?
9. Нужно ли исследование, библиотека или Android plugin?
10. Как система диагностируется?
11. Как она тестируется в headless CI?
12. Требуется ли проверка на реальном Android?
13. Как изменение влияет на saves/schema?
14. Как оно влияет на packages/update/rollback?
15. Требуется ли новая APK-сборка, и почему?
16. Нужны ли docs/release metadata?

## Главные принципы

Eirdan — набор самостоятельных систем с чёткими владельцами, интерфейсами, диагностикой и контролируемыми зависимостями, а не набор случайно связанных сцен и файлов.

APK — runtime, а не база всех изменяемых значений игры.

Игровые данные должны быть максимально authorable и переопределяемыми без изменения исходного кода там, где это не нарушает целостность системы.

Новая система без тестируемости и диагностики не считается законченной.

Старые наработки сохраняются до проверенного переноса; переносится поведение и контракт, а не технический долг старой платформы.
